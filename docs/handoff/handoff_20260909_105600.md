## 1. 任务背景与核心痛点

在发票夹页面 (`#business` / invoice list) 的 `yn-invoice-audit-toolbar` 左侧新增【**⚡ 生成费用记录**】按钮。
在上一轮开发中，由于直接调用了单据明细编辑页的保存接口 `validateAndSaveExpenseRecord`，触发了严格的表单必填项校验（报 `无法判断支出类型` / `费用分类必填` / `出差城市必填` 等），导致 49 笔保存全部失败。

用户明确要求：
**费用记录生成时 分批处理**：
1. **批次一（合并批次）**：将识别出的需要合并的发票（同日同期出租车与过路费）合并生成费用记录（1笔费用挂载多张发票）；
   - 参考抓包：`assets/api ext/are-capture-generic-2026-09-09T02-25-15-171.jsonl`
2. **批次二（逐条批次）**：将其余发票使用平台默认接口逐条生成费用记录；
   - 参考抓包：`assets/api ext/are-capture-generic-2026-09-09T02-20-48-812.jsonl` 与 `assets/api ext/ync37.yuanian.com-002-报销批量助手-费用类型.har`。

## 2. 核心架构与逆向分析突破

### 2.1 平台原生生成链路逆向发现
通过深度剖析 `assets/api ext/ync37.yuanian.com-002-报销批量助手-费用类型.har` 与前端源码 `0_263e49b67d359e34c772.js`，明确了元年云发票夹转费用记录的**真实底层契约**：
1. `POST /fssc/standbyInvoiceController/batchExpenseCheck`
   - 入参：`{ source: "pc", invoiceMainIds: ["id1", "id2", ...] }`
   - 出参：返回合规的标准费用草稿数据结构 `data.expenseRecordDataVOList`；
2. `POST /fssc/expenseClaim/expenseRecord/initAndSaveExpenseRecordData`
   - 入参：直接传入 `expenseRecordDataVO` 对象；
   - **多发票合并原生支持**：在 `expenseRecordInvoiceVOList` 中挂载多个子发票对象（`{ invoiceVO: taxiVO, position: 1 }, { invoiceVO: tollVO, position: 2 }`），后端会自动累加两张发票金额（如 ¥272 + ¥32 = ¥304），自动标记 `invoiceCount: 2`；
   - **草稿免校验直接入库**：直接入库为 `status: "NO_REIMBURSE"` 状态草稿，完全绕过表单级字段必填项校验！

### 2.2 宿主原生 HTTP 客户端动态萃取 (`getNativeHttp`)
- 元年云前端采用 webpack 封装的 axios 实例，携带包含 `eicds`、`v` 在内的全量动态防逆向与会话签名头；
- 新增 `getNativeHttp(win)` 模块：通过 `webpackJsonp` 动态萃取宿主底座 `nativeHttp`（具备 `post`, `getHt` 方法），完全以宿主原生身份发起 API 请求，彻底杜绝自建 fetch 报“登录失效，请重新登录”的问题，同时保留 `apiRequest` 作为全功能兜底。

### 2.3 两批次分流算法 (Two-Batch Partitioning)
- **步骤 1**：全选提取发票主键，调用 `batchExpenseCheckApi` 批量换取有效 VO 列表；
- **步骤 2**：调用 `bindTollsToTaxiExpenses` 识别同日同期出租车与过路费组合；
- **步骤 3（批次一）**：针对每组出租车+过路费，合并构造包含多张 `invoiceVO` 的 `expenseRecordDataVO`，并从待办中剔除；
- **步骤 4（批次二）**：将其余单发票保留在逐条组中；
- **步骤 5（并发写入）**：批次一顺序保存，批次二以 4 线程并发（`mapConcurrent`）极速入库。
