## 1. 任务背景与用户核心反馈

- **用户反馈**：
  > “航班保存可以 但火车班次保存失败  
  > 或许是火车的班次不是必填项？”
- **复现特征**：
  - 用户在“批量修改费用信息”表格中，针对「火车公交车票（電車Bus代）」记录填写了出发地、到达地、起程日期、到达日期；
  - 但列头为“航班/车次”的单元格持续被大红框标红，显示 `必填`；
  - 用户尝试在该单元格填入车次（如 G1234）并点击保存，保存刷新后，出发地/到达地/起程日期/到达日期完整保存回显，但该单元格再次变为空，且依然标红显示 `必填`。

## 2. 真实系统契约逆向事实 (Root Cause)

我们在真实环境通过接口直接调取了元年云对该类型（ID `0356c4c2b14de1653e55bb00bc610000`）的官方元数据定义（`getExpenseTypeFieldRuleListAndAllValueVO`），得出确定性结论：

1. **费用主表不存在车次（TRAIN_NUM）字段**：
   - 飞机票官方定义了 `FLIGHT_NUM`（航班号），因此飞机票能够原生保存航班号；
   - 火车公交车票在元年云官方模型中**只有 4 个差旅移动核心字段**：
     - `START_ADDRESS` (出发地/站)
     - `END_ADDRESS` (到达地/站)
     - `TRAIN_START_DATE` (出发日期)
     - `TRAIN_END_DATE` (到达日期)
     - `BUSINESS_DATE` (业务日期) / `AMOUNT` (金额) / `DESCRIPTION` (说明)
   - 系统底层**根本没有设计 `TRAIN_NUM` 或任何包含“车次/班次”的字段**！
2. **车次的归属层级**：
   - 火车票的车次（如 G1234）仅存在于发票 OCR 明细（发票子行的 `trainNo`）中，属于单张票据凭据数据，不属于费用主记录；
3. **前端误判与保存盲推**：
   - 前端代码 `isDynamicColumnApplicable` 错误地将 `dynTransitNo`（航班/车次）赋予了 `TRAIN`；
   - 当该字段在主表中读取不到时，前端触发了 `yn-bem-dyn-cell-empty`（红框）并提示 `placeholder="必填"`；
   - `batchUpdateExpenseRecordsApi` 试图向后端推送 `TRAIN_NUM`，由于字段不存在被后端忽略，导致每次重开弹窗都在循环标红。

## 3. 核心修复落地方案 (v4.34.9)

### 3.1 视图与交互规范重塑 (`src/ui/batchEditExpenseModal.ts`)
1. **列头精准重命名**：
   - 将原歧义列名 `航班/车次` 修正为 **`航班号`**，明确该列为主体支持航班号的飞机票专属列；
2. **动态适用列剔除**：
   - `isDynamicColumnApplicable` 中，`TRAIN` 的适用列从包含 `dynTransitNo` 修正为仅包含：
     ```typescript
     if (category === 'TRAIN') {
         return ['dynFrom', 'dynTo', 'dynStartDate', 'dynEndDate'].includes(colKey);
     }
     ```
   - 火车票行在该列优雅显示为 `-`（N/A），彻底消除误判红框与“必填”拦截；
3. **清理存取与快捷栏**：
   - 从 `getGroupDynamicFieldValue` 与 `setGroupDynamicFieldValue` 中移除 `TRAIN` 对应的 `dynTransitNo`；
   - 移除顶部批量工具栏中多余的“车次”输入框与行单据编辑模态框中的“车次编号”框；
4. **AI 推断与规则清理**：
   - 清理 `handleAiInference` 中对 `TRAIN` 的 `dynTransitNo` 规则推断与大模型候选字段；

### 3.2 费用保存 API 清洗 (`src/services/expenseService.ts`)
- 彻底移除 `batchUpdateExpenseRecordsApi` 中无效的 `ensureExpenseRowField(rowDatas, 'TRAIN_NUM', ...)` 调用，确保 Payload 100% 契合元年云后端 Schema。
