## 1. 任务背景与用户核心诉求

1. **往返机票双航班号**：
   - 用户反馈：一张发票涵盖往返行程时（例如“8月24日 上海-大连往返机票 1746 CZ6534/CZ6523”），原逻辑无法准确推断并填写往返两个航班号，要求生成格式如 `CZ6534/CZ6523`。
2. **未识别费用类型（UNIDENTIFIED）纳管与必填字段一并补齐**：
   - 要求在提示词中定义标准系统费用类型规范字典，将“未知类型/未分类”条目送入大模型，并在推断中一并识别目标费用类型（`targetExpenseTypeId` / `targetExpenseTypeName`）及对应的专属必填字段。
3. **表格筛选全选交互重构**：
   - 用户反馈：“UI 全选逻辑有问题，有筛选的情况下，全选应该只针对筛选结果而不是整表。诸如此类表格设计问题，请参考相关领域最佳实践自查。”

## 2. 核心技术落地与架构演进

### 2.1 往返航班号识别与防项目号干扰
- **算法位置**：`src/ui/batchEditExpenseModal.ts` 中的 `extractFlightNumFromText`。
- **关键防御**：严密过滤项目编号格式（如 `X2607-001`、`PRJ-001`），杜绝因旧正则中的字母加数字误将项目号识别为航班号；
- **提取优先级**：① 发票 `trainNo` ➔ ② 出差排期文本 `itineraryText`（按金额/日期/航线精准对齐行） ➔ ③ `remarks` ➔ ④ `fileName`。
- **说明解耦**：彻底移除从 `group.description` 提取航班号的缺陷（因为说明包含外驻人名和项目号，绝不包含真实航班）。

### 2.2 未识别类型（UNIDENTIFIED）智能归类补齐
- **双层识别管道**：
  - Zero-LLM 规则层（0ms）：通过发票明细关键词秒级自动识别系统类型；
  - LLM 深度认知层：下发 6 大标准费用类型真实 UUID（飞机票、火车票、住宿费、出租车、通信费、交通费-其他）及专属必填字段规范；
  - 智能推断结果解析引擎自动完成类型变更（`newExpenseTypeId` / `newExpenseTypeName`）与对应 `dynamicFields` 一体化回填。

### 2.3 工业级表格交互规范重构 (遵循 Ant Design / W3C 标准)
- **筛选态全选范围铁律**：有筛选激活时，表头复选框（`#yn-bem-th-select-all`）和工具栏“全选”按钮（`#yn-bem-qa-select-all`）严格仅针对当前筛选集（`filtered`），绝对不污染底表不可见行；
- **批量操作作用域隔离安全守卫 (Batch Actions Scope Guard)**：
  - 批量应用按钮（`#yn-bem-btn-apply`）、业务日期同步（`#yn-bem-qa-sync-earliest-date`）、AI 智能推断（`handleAiInference`）全部注入作用域守卫：
    `const targetGroups = modalState.groups.filter(g => modalState.selectedRecordIds.has(g.expenseRecordId) && (!isFiltering || filtered.some(f => f.expenseRecordId === g.expenseRecordId)));`
  - 彻底杜绝了用户筛选某城市（如大连）后执行批量修改意外把全表 64 笔全部覆盖的历史灾难级缺陷！
- **全不选与反选联动**：
  - 全不选在筛选态仅取消筛选内勾选；反选在筛选集内反转并保留筛选外状态；
- **表头复选框半选（`indeterminate`）精准联动**：
  - 部分选中时呈现 `-`，全部选中呈现 `√`，全部取消呈现空；
- **底部状态栏精细化呈现**：
  - 实时区分 `(当前筛选: X 笔)`、`[当前筛选内已选 Y 笔]`，并提供 `⚠️ 筛选外有 Z 笔被选 (点击仅保留筛选内)` 快速安全收敛按钮；
- **全局搜索增强**：
  - 搜索词模糊匹配穿透支持 `g.dynamicFields`（可直接搜索航班号或酒店品牌）。
