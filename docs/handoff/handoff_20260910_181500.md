## 1. 用户核心诉求与根本痛点

用户反馈：“打车是发起打车目的地 为什么不能推断？”，并提供了包含高铁车次（G456、G1738、G1583、G7538）、往返航班（MU5141、MU5142/FM9116、MU5307、MU5306）、住宿酒店（亚朵、全季、璀璨、上引、富悦）及详细起止时刻的辅助排期日程提示词。
此前在批量修改弹窗中，所有出租车记录的「打车始发地」与「打车目的地」均显示红框“必填”，大模型无法推导出具体据点。

---

## 2. 根因技术剖析 (Root Cause Analysis)

1. **发票原生特征与数据管道阻断**：
   - 出租车电子发票与网约车行程单原生票面几乎**没有站点名称**（`stationGetOn` / `stationGetOff` 为空），但其核心特征是具备分钟级精度的**乘车时间**（`timeGetOn` 上车时间、`timeGetOff` 下车时间，如 `09:24 - 09:48`）；
   - 此前 `batchEditExpenseModal.ts` 在组织 `tripTickets` 背景证据链和 `recordsNeedingInference` 待推断记录时，仅向大模型下发了 `stationGetOn`，**完全丢弃了 `timeGetOn` 和 `timeGetOff`**！导致大模型在没有任何时间线索的情况下无从推断。
2. **多发票合并下的索引错位**：
   - 费用记录在合并过路费或多张发票时，`invoices[0]` 可能是过路费，出租车票位于 `invoices[1]`；若机械读取 `inv0` 则时间字段彻底丢失。
3. **推断引擎缺少时空闭环认知指引**：
   - 原 System Prompt 仅有单向的文本提取规则，未告知模型如何结合大交通班次起降到发时刻与出租车具体时间的先后关系展开时空轨迹闭环推理。

---

## 3. 架构优化与核心改进方案

### 3.1 乘车时间全链路精准透传
- 在 `ExpenseRecordExportRow` 与 `ExpenseInvoiceSubItem` 契约中明确增加 `timeGetOn` 字段；
- 在 `batchEditExpenseModal.ts` 中通过智能检索优先定位包含乘车时间的出租车发票：
  ```typescript
  const taxiInv = g.invoices.find(inv => inv.timeGetOn || inv.timeGetOff || inv.stationGetOn || inv.stationGetOff) || inv0;
  ```
- 将 `timeGetOn`、`timeGetOff` 随同金额、日期等作为核心证据链下发给 LLM。

### 3.2 时空轨迹闭环推理认知指引 (Spatiotemporal Trajectory Closed-loop)
在 System Prompt 中深度注入出行场景的客观时空守卫逻辑：
1. **大交通出发首日 (去程日)**：
   - 出发前打车（赴机场/高铁站）：`住所` ➔ 当天出发交通枢纽（如 `上海虹桥机场` / `上海虹桥站`）；
   - 到达后打车（落地外地后赴酒店）：到达交通枢纽（如 `天津滨海机场` / `合肥南站`）➔ 排期表中当天入住酒店（如 `全季酒店...` / `合肥滨湖云谷金融城亚朵酒店`）；
2. **大交通返程末日 (回程日)**：
   - 返程前打车（外地赴机场/火车站）：当天退房酒店 ➔ 外地交通枢纽；
   - 返程到达常驻地后打车（晚间落地回住所）：到达交通枢纽 ➔ `住所`；
3. **在途常驻出差日**：
   - 在当天入住酒店与客户现场之间流转；
4. **实体解析去代称铁律 (Entity Resolution)**：
   - 严禁输出“酒店”、“机场”、“车站”、“Home”等模糊代称，结合排期表与发票上下文严格具体化。
